## Тема: crypto

### Задача 1: My first hash

**Категория:** Crypto / Hashes  
**Стоимость:** 1 балл  
**Итоговый ответ (Флаг):** `CTF{orchestra}`

#### 1. Анализ условия и исходного кода
Нам предоставлен скрипт на языке Python:
```python
import hashlib
from sys import exit

flag = '8f163b472e2164f66a5cd751098783f9'

str = input("Enter the flag\n")
str = hashlib.md5(str.encode())

if str.digest().hex() == flag:
    print("Congrats! You got the flag!")
else:
    print("Nope. Try again!")

exit()
```

**Логика работы программы:**
1. Программа принимает ввод пользователя в переменную `str`.
2. Переведенная в байты строка (`.encode()`) хешируется алгоритмом **MD5** (`hashlib.md5`).
3. Вызов `.digest().hex()` преобразует байтовый хеш в шестнадцатеричную строку (32 символа в диапазоне `0-9a-f`), что полностью эквивалентно стандартному методу `.hexdigest()`.
4. Полученный хеш сравнивается со строкой `8f163b472e2164f66a5cd751098783f9`.

#### 2. Связь с изучаемыми ресурсами
* **Классификация данных:** Если бы у нас не было исходного кода, отправка строки `8f163b472e2164f66a5cd751098783f9` в анализаторы **[dCode.fr](https://www.dcode.fr/cipher-identifier)** или **[Boxentriq](https://www.boxentriq.com/code-breaking/cipher-identifier)** сразу дала бы подсказку: *«Длина строки 32 символа, алфавит Base16 (Hex). Наиболее вероятный тип: MD5 Hash»* (см. раздел [Hex](https://itsecwiki.org/index.php/String_crypto#Hex) на ItSecWiki).
* **Специфика хеш-функций:** В отличие от кодировок (таких как Base64 в **[CyberChef](https://gchq.github.io/CyberChef/)**), алгоритм MD5 криптографически необратим.
* **Инструмент дехеширования:** Для поиска исходного значения по хешу идеально подходит **[CrackStation](https://crackstation.net/)** — сервис, использующий гигантские lookup-таблицы (190 ГБ, 15 млрд записей для MD5/SHA1), собранные из дампов Википедии и утечек паролей.

#### 3. Пошаговое решение

##### Шаг 1: Выбор метода дехеширования
Поскольку математической функции дешифрования MD5 не существует, получить прообраз можно через поиск по готовым таблицам соответствий (Rainbow Tables / Lookup Tables).

##### Шаг 2: Нахождение прообраза через CrackStation
Вбиваем зашифрованную строку `8f163b472e2164f66a5cd751098783f9` в поле поиска **[CrackStation.net](https://crackstation.net/)**. База данных мгновенно находит соответствие среди своих 15 миллиардов записей:
* Тип хеша: `MD5`
* Результат (исходное слово): **`orchestra`**

##### Шаг 3: Проверка (Верификация в терминале)
Для гарантии проверяем найденное слово через Python:
```bash
python3 -c "import hashlib; print(hashlib.md5(b'orchestra').hexdigest())"
# Вывод: 8f163b472e2164f66a5cd751098783f9
```
Результат идеально совпадает с эталоном из кода задачи.

#### 4. Формирование ответа
Оборачиваем слово `orchestra` в требуемый условием формат `CTF{answer}`.

**Флаг:** `CTF{orchestra}`

### Задача 2: какая-то неправильная бинарщина

**Категория:** Crypto / Miscellaneous  
**Стоимость:** 1 балл  
**Итоговый ответ (Флаг):** `sun{exterminate-exterminate-exterminate}`

#### 1. Анализ входных данных
В задаче дан текст, состоящий исключительно из чередующихся слов `beep` и `boop`. 
Подсказка в названии («неправильная бинарщина») указывает на двоичный шифр замены (Binary Substitution), где стандартные цифры `0` и `1` заменены на имитацию звуков робота.

Всего в тексте ровно **328 слов**. Число 328 нацело делится на 8 ($328 / 8 = 41$), что идеально соответствует 41 символу в 8-битном кодировании ASCII.

#### 2. Применение изучаемых ресурсов

* **Анализ структуры (по [dCode.fr](https://www.dcode.fr/cipher-identifier) / [Boxentriq](https://www.boxentriq.com/code-breaking/cipher-identifier)):** Анализаторы определяют текст из двух уникальных токенов как бинарное кодирование (Binary Code).
* **Теория из [InformationSecurity WIKI](https://itsecwiki.org/index.php/String_crypto):**
  1. Раздел **Binary (Процессорные шифры):** строка представляет собой последовательность байтов.
  2. Раздел **Ceasar cipher (Развлечения):** шифр моноалфавитной подстановки со сдвигом (ROT13).
* **Цепочка в [CyberChef](https://gchq.github.io/CyberChef/):** Для автоматического решения в CyberChef строится рецепт (Recipe):
  1. `Find / Replace`: найти `beep`, заменить на `0`.
  2. `Find / Replace`: найти `boop`, заменить на `1`.
  3. `Find / Replace`: удалить пробелы.
  4. `From Binary`: режим 8-bit Byte.
  5. `ROT13`: сдвиг 13.

#### 3. Пошаговое решение

##### Шаг 1: Перевод слов в бинарный код
Выдвигаем гипотезу: `beep` = `0`, а `boop` = `1`. Выполняем подстановку:
```text
00001010 01100110 01101000 01100001 01111011 01110010 01101011 ...
```

##### Шаг 2: Декодирование двоичного кода в символы
Разбиваем битовую строку на байты по 8 бит и переводим по таблице ASCII:
* Первый байт `00001010` (10 в десятичной системе) — это управляющий символ переноса строки (`\n`).
* Остальные 40 байт декодируются в текст:  
  `fha{rkgrezvangr-rkgrezvangr-rkgrezvangr}`

##### Шаг 3: Расшифровка ROT13 (Шифр Цезаря)
Полученная строка по форме совпадает со структурой флага, но вместо ожидаемого по условию префикса `sun{` мы видим `fha{`.
Проверяем смещение букв префикса в латинском алфавите:
* Буква `f` (6-я) смещена относительно `s` (19-я) ровно на 13 позиций ($19 - 6 = 13$).
* Буква `h` (8-я) смещена относительно `u` (21-я) на 13 позиций ($21 - 8 = 13$).
* Буква `a` (1-я) смещена относительно `n` (14-я) на 13 позиций ($14 - 1 = 13$).

Применяем шифр ROT13 (сдвиг алфавита на 13 позиций) ко всему содержимому скобок:
```text
fha -> sun
rkgrezvangr -> exterminate
```

#### 4. Ответ
**Флаг:** `sun{exterminate-exterminate-exterminate}`

### Задача 3: Кот сломал base64

**Категория:** Crypto / Encodings  
**Стоимость:** 2 балла  
**Итоговый ответ (Флаг):** `ctf{Mars1k_l0ves_base64}`

#### 1. Анализ условия и входных данных
Предоставлена строка: `hjY3Rme01hcnMxa19sMHZlc19iYXNlNjR9` (общая длина: 34 символа).
По условию задачи, строка представляет собой пароль в кодировке Base64, в которую случайно попали лишние нажатия клавиш котом. Требуется найти эти артефакты, восстановить валидную строку Base64 и расшифровать её.

#### 2. Применение знаний из базы ресурсов

* **Математические свойства (по [InformationSecurity WIKI](https://itsecwiki.org/index.php/String_crypto#Base64)):**
  Алгоритм Base64 кодирует каждые 3 байта исходных данных (24 бита) в 4 символа ASCII (по 6 бит на символ: $4 \times 6 = 24$). 
  Следовательно, *валидная последовательность Base64 без учета знаков паддинга (`=`) строго обязана иметь длину, кратную 4*.
* **Диагностика сбоя:**
  Длина предоставленной строки равна **34 символам**. Остаток от деления: $34 \pmod 4 = 2$. Это математически доказывает наличие ровно **двух лишних символов** в теле строки.
* **Поведение парсеров (в [CyberChef](https://gchq.github.io/CyberChef/)):**
  При попытке передать строку `hjY3Rme...` в модуль `From Base64` стандартный декодер выдает поврежденные данные на старте, поскольку первые байты парсятся некорректно.

#### 3. Пошаговое решение

##### Шаг 1: Поиск кошачьих следов (Шума)
Из условия нам известен точный формат ожидаемого ответа: `ctf{...}`.
Проведем тестовое кодирование структуры флага в модуле `To Base64`:
* Текст **ctf{...}** в Base64 $\rightarrow$ Y3Rmey4uLn0=

Сверим полученный эталонный префикс с началом зашифрованной строки из задания:
```text
Наша строка:    hj Y3Rme 01hcnMxa19sMHZlc19iYXNlNjR9
Шаблон Base64:     Y3Rme y4uLn0=
```
Очевидно, что совпадение префикса `Y3Rme` начинается ровно с третьего символа. Это доказывает, что кот Марсик нажал клавиши **`h`** и **`j`** в самом начале строки перед скопированным паролем.

##### Шаг 2: Очистка последовательности
Удаляем первые два символа `hj`. Остается строка:
`Y3Rme01hcnMxa19sMHZlc19iYXNlNjR9`

Проверяем длину очищенного текста: ровно **32 символа**. Число 32 делится на 4 без остатка ($32 / 4 = 8$ блоков по 4 символа), что подтверждает целостность данных.

##### Шаг 3: Декодирование пароля
Передаем очищенную строку `Y3Rme01hcnMxa19sMHZlc19iYXNlNjR9` в модуль `From Base64` инструмента **CyberChef**. На выходе мгновенно получаем восстановленный оригинальный пароль: `ctf{Mars1k_l0ves_base64}`.

#### 4. Ответ
**Флаг:** `ctf{Mars1k_l0ves_base64}`

### Задача 4: базированно

**Категория:** Crypto / Base Encodings  
**Стоимость:** 2 балла  
**Итоговый ответ (Флаг):** `ctf{w0w_th4ts_crypt0_4nd_5tufF}`

#### 1. Анализ легенды и входных данных
Автор задания пишет: *«постарался закодировать сообщение МАКСИМАЛЬНО базированно. я справился?»*. 
На сленге CTF слово «базировано» (Based) — это прямая отсылка к семейству алгоритмов кодирования **Base-X**. Подтверждением служит огромная строка, содержащая широкий спектр печатаемых символов ASCII.

#### 2. Применение изучаемых ресурсов

* **Пошаговая идентификация (по [dCode.fr](https://www.dcode.fr/cipher-identifier) / [Boxentriq](https://www.boxentriq.com/code-breaking/cipher-identifier)):**
  Анализ каждого промежуточного слоя через анализаторы шифров показывает регулярное сужение используемого алфавита. Анализаторы последовательно предлагают: *Base92 $\rightarrow$ Ascii85 $\rightarrow$ Base64 $\rightarrow$ Base62 $\rightarrow$ Base58 $\rightarrow$ Base45 $\rightarrow$ Base32 $\rightarrow$ Hex*.
* **Теория из [InformationSecurity WIKI](https://itsecwiki.org/index.php/String_crypto):**
  В энциклопедии подробно разобраны популярные кодировки семейства: **Hex/Base16**, **Base32**, **Base64**, **Base85/Ascii85**.

#### 3. Пошаговое декодирование каскада

##### Шаг 1: Декодирование Base92
Передаем зашифрованный текст в декодер **Base92**. Объем данных сокращается до 700 байт. Получаем читаемый ASCII-текст в кодировке Ascii85.

##### Шаг 2: Декодирование Base85 (Ascii85)
Декодируем алгоритмом **Ascii85**. Строка сокращается до 560 символов:
`RU9tdjl5S1FJUm5XSEp0Q28xSW9kbEpFeVM1eXh4e...` (стандартный алфавит Base64).

##### Шаг 3: Декодирование Base64
Применяем стандартный **Base64**. Текст уменьшается до 418 байт:
`EOmv9yKQIRnWHJtCo1IodlJEyS5yxxyjsat0inacnz...` (алфавит из 62 букв и цифр).

##### Шаг 4: Декодирование Base62
Строка содержит исключительно цифры `0-9`, буквы `a-z` и `A-Z` (без спецсимволов). Расшифровываем из **Base62**. Остается 311 байт:
`kyHcKCw1qckyTxibKWKVfqW4XaLnbPNZL77HpKaL...`

##### Шаг 5: Декодирование Base58
Проверка символов 311-байтовой строки выявляет отсутствие визуально похожих знаков (`0`, `O`, `I`, `l`). Это знаменитый алфавит Биткоина — **Base58**. После расшифровки получаем 228 символов:
`+09%IBNB8+IB:X8TL6UY9JH8UY9ECA71AKIBS09...`

##### Шаг 6: Декодирование Base45
Алфавит из цифр, заглавных букв и точечного набора знаков (`$ % * + - . / :`) в точности соответствует стандарту QR-кодов **Base45** (RFC 9285). Декодируем текст в 152 символа:
`GYZSANZUEA3DMIBXMIQDONZAGMYCANZXEA2W...====`

##### Шаг 7: Декодирование Base32
Буквы одного регистра (`A-Z`), цифры `2-7` и характерный паддинг `====` однозначно определяют **Base32**. После расшифровки получаем строку:
`63 74 66 7b 77 30 77 5f 74 68 34 74 73 5f...`

##### Шаг 8: Финальное декодирование Base16 (Hex)
Перед нами шестнадцатеричные коды символов ASCII, разделенные пробелами (`63` = `c`, `74` = `t`, `66` = `f`, `7b` = `{`). Убираем пробелы и декодируем из **Base16**.

На выходе получаем открытый текст: `ctf{w0w_th4ts_crypt0_4nd_5tufF}`

#### 4. Вывод
Автор блестяще справился с задумкой: сообщение было зашифровано невероятной «матрешкой» из 8 последовательных систем счисления — от Base92 до Base16.

**Флаг:** `ctf{w0w_th4ts_crypt0_4nd_5tufF}`

### Задача 5: много цезарей

**Категория:** Crypto / Classical Ciphers  
**Стоимость:** 3 балла  
**Итоговый ответ (Флаг):** `ENO{th3_d1ffer3nce5_m4ke_4ll_th3_diff3renc3}`

#### 1. Разбор алгоритма шифрования
Нам предоставлен скрипт на Python:
```python
import re
import string

text = open('text.txt', 'r').read().lower()
flag = open('flag.txt', 'r').read().strip()[4:-1].replace('_', '+')
chars = string.ascii_letters + string.digits + '+/='
```

**Логика работы программы:**
1. Текст из файла `text.txt` переводится в нижний регистр (`.lower()`), то есть состоит исключительно из букв `a-z`, пробелов и знаков препинания.
2. Из флага формата `ENO{flag}` вырезается оболочка скобок (`[4:-1]`), а все символы подчеркивания `_` заменяются на `+`.
3. Формируется кастомный алфавит `chars` мощностью 65 знаков: строчные буквы (0–25), заглавные (26–51), цифры (52–61) и символы `+`, `/`, `=` (62–64).
4. В цикле сканируется исходный текст:
   * Все пробелы, точки, запятые и переносы строк печатаются **без изменений**.
   * Каждое слово (непрерывная цепочка букв `a-z`) сдвигается по алфавиту `chars` шифром Цезаря на величину, равную индексу очередного символа флага `flag[count % len(flag)]`. Затем счетчик слов `count` увеличивается на 1.

В отличие от классического шифра Виженера, где шаг сдвига меняется на каждой *букве*, здесь полиалфавитный сдвиг происходит **пословно** (один символ флага определяет сдвиг для всего слова целиком).

#### 2. Связь с изучаемыми ресурсами

* **Теория из [InformationSecurity WIKI](https://itsecwiki.org/index.php/String_crypto):**
  1. Раздел **Ceasar cipher (Развлечения):** моноалфавитный циклический сдвиг. В нашей задаче Цезарь применяется со сдвигом $N$, где $N$ — позиция буквы ключа в алфавите `chars`.
  2. Раздел **Vigenère cipher (Развлечения):** полиалфавитный шифр, использующий повторяющийся ключ. Наш алгоритм представляет собой оригинальную пословную вариацию Виженера.
* **Классификация паттерна (по [dCode.fr](https://www.dcode.fr/cipher-identifier) / [Boxentriq](https://www.boxentriq.com/code-breaking/cipher-identifier)):**
  Анализаторы определяют зашифрованный текст с сохраненной пунктуацией как подстановочный шифр со сдвигом (Caesar / Vigenere / ROT-N).
* **Модули [CyberChef](https://gchq.github.io/CyberChef/):**
  Рецепт `ROT13 Brute Force` (или перебор `Caesar Cipher`) в CyberChef позволяет за секунду наглядно проверить все возможные варианты расшифровки для любого зашифрованного токена.

#### 3. Пошаговое решение

##### Шаг 1: Токенизация текста
Поскольку пунктуация и пробелы не подвергались шифрованию, разбиваем вывод на отдельные слова. Получаем ровно **95 зашифрованных слов**.

##### Шаг 2: Словарный перебор сдвигов
Для каждого из 95 слов проверяем все 65 возможных сдвигов назад. Практически всегда ровно один вариант сдвига дает валидное английское слово в нижнем регистре (`a-z`):
* Слово 0: `AtvDxK` (сдвиг на 19 / символ `t`) $\rightarrow$ `hacker`
* Слово 1: `lAopjz` (сдвиг на 7 / символ `h`) $\rightarrow$ `ethics`
* Слово 2: `/i` (сдвиг на 55 / символ `3`) $\rightarrow$ `is`
* Слово 3: `+` (сдвиг на 62 / символ `+`) $\rightarrow$ `a`
* Слово 4: `vhw` (сдвиг на 3 / символ `d`) $\rightarrow$ `set`
* Слово 5: `c6` (сдвиг на 53 / символ `1`) $\rightarrow$ `of`
* Слово 6: `uwnshnuqjx` (сдвиг на 5 / символ `f`) $\rightarrow$ `principles`
* Слово 7: `ymfy` (сдвиг на 5 / символ `f`) $\rightarrow$ `that`
* Слово 8: `kymhi` (сдвиг на 4 / символ `e`) $\rightarrow$ `guide`
* Слово 9: `Kyv` (сдвиг на 17 / символ `r`) $\rightarrow$ `the`
* Слово 10: `47+3l/eh` (сдвиг на 55 / символ `3`) $\rightarrow$ `behavior`

#### 1. Анализ условия и легенды задачи
В задании дан архив `broken_picture.zip`, внутри которого находится графический файл, не открывающийся стандартными средствами операционной системы.

#### 2. Выдвижение форензических гипотез
На этапе предварительного анализа были сформулированы 5 основных гипотез дефекта изображения:
1. *Поврежденные магические байты (File Signature / Magic Bytes) — Вероятность 80%.* Операционные системы распознают тип файла не по расширению `.png` или `.jpg`, а по уникальной сигнатуре в самом начале заголовка. В CTF первые байты часто затирают нулями.
2. *Обнуленная высота картинки (IHDR Height Corruption) — Вероятность 10%.* Повреждение метаданных разрешения изображения.
3. *Ложное расширение.* Под маской картинки скрывается иной формат (архив, исполняемый файл или аудио).
4. *Сокрытие ответа в ASCII-строках (EXIF / Strings).* Текст внутри бинарного кода.
5. *Склейка файлов (File Carving).* Наличие скрытого прикрепленного файла в конце бинарника.

#### 3. Подтверждение гипотезы и связь с ресурсами
Проверка файла подтвердила **Гипотезу 1**: сигнатура файла была затерта. Была произведена замена самой первой пары цифр в левом верхнем углу (смещение `00000000`) `AE 71 00 FF 3D 62 24 6D` на `89 50 4E 47 0D 0A 1A 0A`, после чего файл открылся.

Для замены сигнатуры согласно изучаемым ресурсам подходят:
* Онлайн-рецепт в **[CyberChef](https://gchq.github.io/CyberChef/)** (`To Hex` $\rightarrow$ правка Hex-строки $\rightarrow$ `From Hex` + `Render Image`).
* Скрипт на **Python** в консоли (открытие в режиме `r+b` и перезапись байтов через `f.seek(0)` + `f.write(...)`).
* Консольные команды Linux (`printf + dd`).
* Графический Hex-редактор на компьютере (**HxD** / *010 Editor*).

#### 4. Практическая реализация решения

Формат `.mkv` (Matroska) разрабатывался не как простой видеоформат, а как расширяемая мультимедийная «матрешка». Контейнер способен инкапсулировать множество независимых параллельных потоков данных: видео, несколько аудиодорожек, главы и теги. Основной видеоряд часто служит отвлекающим маневром.

Прикреплен документ электронной таблицы Microsoft Excel. В легенде сказано: *«говорят, что тяжело найти иголку в стоге сена...»*.

#### 2. Архитектура формата .XLSX
Современные офисные документы `.xlsx` (Office Open XML) технологически представляют собой стандартные **ZIP-архивы**, хранящие данные в наборе XML-файлов. 
Вместо дублирования строк в ячейках листа Excel сохраняет абсолютно все уникальные текстовые значения книги в едином глобальном реестре — файле **`xl/sharedStrings.xml`**.

#### 3. Пошаговое решение

##### Шаг 1: Работа с контейнером
Берём предоставленный по условию табличный документ `flags.xlsx` и рассматриваем его внутреннюю структуру как стандартный `.zip`-архив.

##### Шаг 2: Анализ XML-словаря
Вскрываем архив и открываем реестр строк `xl/sharedStrings.xml`. Внутри обнаруживается массив ровно из **40 000 текстовых тегов** `<t>...</t>`. 

##### Шаг 3: Автоматизированный поиск аномалии
Анализ структуры показывает отвлекающий шум: ячейки забиты повторяющимся словом `haystack` и фейковыми флагами `fake_flag1`, `fake_flag2`... `fake_flag39999`.

Для мгновенного отсева мусора выполняем фильтрацию скриптом на Python в терминале:
```bash
python3 -c '
import zipfile, re
with zipfile.ZipFile("flags.xlsx") as z:
    xml = z.read("xl/sharedStrings.xml").decode("utf-8", errors="ignore")
tags = re.findall(r"<t[^>]*>(.*?)</t>", xml)
print([t for t in tags if not t.startswith("fake_flag") and "haystack" not in t])
'
# Вывод: ['h3ll_0f_4n_3xc3l']
```

Скрипт мгновенно отсеивает 39 999 шумовых строк и находит единственную уникальную запись: **`h3ll_0f_4n_3xc3l`** (*«адский эксель»*).

#### 4. Ответ
Оборачиваем найденный текст в требуемую условием конструкцию `CTF{...}`.

**Флаг:** `CTF{h3ll_0f_4n_3xc3l}`

* **Математика сетки:** Размер каждого из 400 тайлов составляет ровно 20х20 пикселей. Квадратный корень $\sqrt{400} = 20$. Это доказывает, что перед нами разрезанная мозаика (цифровой пазл), которую необходимо собрать в единый квадрат холста 20 на 20 ячеек.

#### 4. Пошаговое решение

##### Шаг 1: Извлечение архива
Отсекаем заголовок JPEG до маркера `FF D9` и сохраняем оставшуюся часть как `secret.zip`. Распаковываем директорию `secrets/`.

##### Шаг 2: Анализ фрагментов мозаики
Внутри находятся 400 тайлов. Изучение имен (`piece_0.png` ... `piece_399.png`) показывает, что числовой индекс в названии строго соответствует порядковому номеру фрагмента.

##### Шаг 3: Программная склейка пазла
Чтобы не собирать мозаику вручную, пишем лаконичный скрипт на Python (библиотека `Pillow`), который объединяет тайлы в сетку 20х20 в порядке возрастания их номеров:
```python
from PIL import Image
im0 = Image.open("secrets/piece_0.png")
w, h = im0.size # (20, 20)
grid = Image.new("RGB", (w * 20, h * 20))

for i in range(400):
    tile = Image.open(f"secrets/piece_{i}.png")
    grid.paste(tile, ((i % 20) * w, (i // 20) * h))
grid.save("assembled.png")
```
Общее разрешение собранного изображения: $400 \times 400$ пикселей.

##### Шаг 4: Сканирование результата
Восстановленное изображение `assembled.png` представляет собой четкий классический QR-код. Чтение QR-кода через стандартный декодер выдает скрытую строку ответа:
`shctf{s0_l0ng_4nd_th4nks_f0r_4ll_th3_flags}`

#### 5. Ответ
**Флаг:** `shctf{s0_l0ng_4nd_th4nks_f0r_4ll_th3_flags}`

## Тема: web

### Виды web-задач
* **Чёрный ящик (Black-box):** исходный код приложения недоступен. Исследование ведётся снаружи — через HTTP-запросы, интерфейс, HTML-разметку и сетевой трафик.
* **Белый ящик (White-box):** предоставлены исходники сервера. Анализ ведётся изнутри — поиск захардкоженных паролей, небезопасной логики авторизации, SQL-инъекций.

### Примерный алгоритм решения web-задач
1. Открыть сайт — понять, что за приложение. При необходимости зарегистрироваться.
2. Проверить `http://site.com/robots.txt` — есть ли скрытые пути.
3. Просмотреть исходный код страницы — поискать HTML-комментарии, скрытые поля форм, необычные ссылки.
4. Открыть DevTools (`F12`) → вкладка **Network**, повторить целевые действия и изучить запросы/ответы (в т.ч. заголовки).
5. `dirsearch` — перебор скрытых директорий и файлов по словарю.
6. Параметры URL — если есть числовые `id`, попробовать их менять (атака IDOR).
7. **Burp Suite** — перехват и модификация запроса, когда нужна тонкая настройка.
8. Анализ исходников (только для «белого ящика») — пароли, небезопасная логика, SQL.

### Основные ресурсы и инструменты
1. **Браузер + DevTools (`F12`)** — вкладки *Elements*, *Network*, *Application*, *Console*.
2. **`curl`** — консольный HTTP-клиент (доступен в Git Bash на Windows 11 «из коробки»).
3. **`robots.txt`** — стандартный файл-карта запретных зон сайта.
4. **View Source (`Ctrl+U`)** — просмотр «сырого» HTML для поиска комментариев и скрытых полей.
5. **[Burp Suite](https://portswigger.net/burp) / [Caido](https://caido.io/)** — прокси для перехвата и модификации запросов.
6. **[dirsearch](https://github.com/maurosoria/dirsearch)** / **[ffuf](https://github.com/ffuf/ffuf)** — перебор скрытых директорий и файлов.
7. **[OWASP Top-10](https://owasp.org/www-project-top-ten/)** — справочник по классическим web-уязвимостям (IDOR, XSS, SQLi и т.д.).

### Задача 10: я по частицам...

**Категория:** Web / Recon (Information Disclosure)
**Стоимость:** 1 балл
**Итоговый ответ (Флаг):** `CTF{y0u_4r3_r3c0n_m4st3r}`

#### 1. Анализ условия и легенды задачи
Дан адрес учебного веб-приложения: `http://10.10.10.61/`.
Легенда: *«Разработчики оставили несколько сообщений, позволяющих открыть секретное сообщение от них. Можешь поискать?»*
Подсказка задаёт строгий порядок склейки: **`prefix` + `token` + `suffix`**.

Ключевые слова *«несколько сообщений»* и низкая стоимость (1 балл) указывают на классический **recon-warm-up**: каждая из трёх частей спрятана в одном из «канонических» мест web-приложения, которые проверяются первыми пунктами алгоритма для «чёрного ящика».

#### 2. Карта находок (по алгоритму Black-box)
Разработчики разложили три части по разным «каноническим» точкам утечки информации:

| Часть | Место находки | Пункт алгоритма |
|-------|---------------|-----------------|
| `prefix` | HTML-комментарий `<!-- ... -->` в исходном коде главной страницы | п. 3 «Исходный код» |
| `suffix` | Служебный комментарий `# ...` внутри файла `robots.txt` (не `Disallow`, а строка-заметка) | п. 2 «robots.txt» |
| `token`  | Файл в директории `/backup/`, обнаруженной перебором путей | п. 5 «dirsearch» |

#### 3. Пошаговое решение

##### Шаг 1. Поиск `prefix` — HTML-комментарий на главной
Запрашиваем главную страницу и выводим только строки с HTML-комментариями. В Git Bash под Windows 11:
```bash
curl -s http://10.10.10.61/ | grep -i '<!--'
```
Альтернатива через браузер: открыть сайт → `Ctrl+U` (View Source) → найти строки, начинающиеся с `<!--`.

В исходном коде обнаруживается «забытый» разработчиками комментарий, из которого извлекается первая часть строки:

**`prefix = r3c0n_`**

##### Шаг 2. Поиск `suffix` — комментарий в `robots.txt`
Читаем стандартный файл-карту запретных зон:
```bash
curl -s http://10.10.10.61/robots.txt
```
Здесь важно смотреть не только на директивы `User-agent:` и `Disallow:`, но и на **строки-комментарии, начинающиеся с `#`** — по стандарту роботы их игнорируют, поэтому админы часто оставляют там служебные заметки «для себя». В файле обнаруживается такая строка:
```text
# infra: remember to rotate the old diag suffix "9f3a2c" before next deploy
```
Внутри кавычек — вторая часть строки:

**`suffix = 9f3a2c`**

##### Шаг 3. Поиск `token` — перебор скрытых директорий (`dirsearch`)
На поверхности (HTML-комментарии, метатеги, HTTP-заголовки, `robots.txt`) третьей строки нет. Значит запускаем словарный перебор путей утилитой `dirsearch`.

**Установка:**
```bash
python -m pip install dirsearch
```

**Траблшутинг под Python 3.14 (Windows).**
При первом запуске возникает ошибка:
```text

```
Причина: в свежих версиях `setuptools` (≥ 81) модуль `pkg_resources` вынесен наружу, а `dirsearch` в строке 23 своего кода всё ещё импортирует его старым способом. Фикс — откатить `setuptools` до совместимой версии:

```text
[13:28:21] 200 -    2KB - /backup
[13:28:21] 200 -    2KB - /backup/
```

##### Шаг 4. Сборка секретного пути
Склеиваем найденные части в заданном условием порядке `prefix + token + suffix`:
```text
r3c0n_  +  m4st3r_  +  9f3a2c   →   r3c0n_m4st3r_9f3a2c
```

На этом этапе важно не остановиться: полученная строка **не является финальным флагом**, а служит секретным идентификатором для перехода на скрытую страницу приложения.

##### Шаг 5. Переход по собранному URL

### Задача 11: а что у тебя?

**Категория:** Web / Broken Access Control (IDOR)
**Стоимость:** 1 балл
**Итоговый ответ (Флаг):** `CTF{vuln3rab1l1ty_w1th_funny_n4m3}`

#### 1. Анализ условия и легенды задачи
Дан адрес корпоративного портала *«Nimbus Workspace»*: `http://10.10.10.62/`.
Легенда: *«Команда разработчиков запустила новый корпоративный портал для совместной работы и очень гордится своим личным кабинетом»*.

Ключевые сигналы условия:
* **«Личный кабинет»** — значит есть регистрация и приватные страницы пользователей.
* **Название «а что у тебя?»** — прямой намёк на «подглядывание» в чужой кабинет.
* Стоимость 1 балл — типовой warm-up на первую же уязвимость из OWASP Top-10: **A01 Broken Access Control**, а именно её частный случай **IDOR** (Insecure Direct Object Reference).

**IDOR** — уязвимость, при которой приложение обращается к внутренним объектам (записям БД, файлам, пользователям) по идентификатору из запроса и **не проверяет**, имеет ли текущий пользователь право на этот объект. В результате достаточно поменять чужой `id` в URL или форме, чтобы получить доступ к чужим данным.

#### 2. Применение изучаемых ресурсов
* **Браузер** — регистрация, вход, работа с UI личного кабинета.
* **Функция портала «Найти коллегу»** — штатная форма поиска карточки пользователя по его идентификатору (`id`). Именно она и оказалась уязвимой точкой входа.
* **[OWASP Top-10 → A01 Broken Access Control](https://owasp.org/Top10/A01_2021-Broken_Access_Control/)** — теоретическая база: приложение обязано проверять права доступа к каждому объекту на стороне сервера, а не полагаться на то, что «пользователь просто не узнает чужой id».

#### 3. Пошаговое решение

##### Шаг 1. Регистрация и вход в личный кабинет
Открываем `http://10.10.10.62/` в браузере. Приложение — корпоративный портал *Nimbus Workspace*. Проходим стандартную регистрацию (произвольные логин/пароль) и логинимся. После входа попадаем в **Панель управления** (Dashboard), где среди прочих виджетов присутствует блок функций для работы с коллегами.

##### Шаг 2. Обнаружение уязвимой функции «Найти коллегу»
В панели управления имеется функция:

> **Найти коллегу** — *Найдите карточку коллеги по его идентификатору в Nimbus.*

Форма принимает единственный параметр — числовой `id` пользователя. Это классическая точка возникновения IDOR: разработчик реализовал поиск «по id», но, судя по названию задачи, забыл проверить, имеет ли текущий пользователь право видеть **приватные** поля запрошенной карточки.

##### Шаг 3. Атака IDOR — подстановка `id = 1`
В корпоративных системах пользователь с идентификатором **`1`** — это, как правило, первый заведённый аккаунт: администратор, установщик системы, «нулевой» сотрудник. Именно его карточка чаще всего содержит служебные заметки и учётные данные.

В форму «Найти коллегу» вводим `id = 1` и отправляем запрос. Портал послушно отдаёт полную карточку системного администратора, включая раздел, который **должен был быть виден только владельцу профиля**:

```text
Personal notes (visible only to you)

Internal note - rotate service credentials weekly.
SYSTEM FLAG: CTF{vuln3rab1l1ty_w1th_funny_n4m3}
```

##### Шаг 4. Извлечение флага
Строка `SYSTEM FLAG: ...` в личных заметках админа содержит готовый ответ. Никакой доп. обработки не требуется — флаг уже в формате `CTF{...}`.

#### 4. Разбор уязвимости
Приложение допустило две связанные ошибки:
1. **Отсутствие авторизации на уровне объекта.** Эндпоинт поиска коллеги возвращает карточку любого пользователя по его `id`, не проверяя, кто именно её запрашивает.
2. **Утечка приватных полей.** Поле `Personal notes` с пометкой *«visible only to you»* фактически видно всем — заявленное ограничение реализовано только в UI-подписи, но не на сервере.

Правильное поведение: сервер должен либо возвращать только «публичные» поля карточки (имя, должность, отдел), либо проверять `request.user.id == requested_id` для приватных секций.

#### 5. Ответ
**Флаг:** `CTF{vuln3rab1l1ty_w1th_funny_n4m3}`

#### 2. Связь с изучаемыми ресурсами и классификация уязвимости
Данная задача относится к категории **Weak JWT Cryptography / PRNG Predictability** (Слабая криптография и предсказуемость генератора псевдослучайных чисел).

   * `file_param3 = ignore_it(file_param2)` (Вторая проверка на точки/слэши)
   * `file_param4 = another_useless_function(file_param3)` (Второе URL-декодирование)
   * `file_param5 = another_useless_function(file_param4)` (Третье URL-декодирование)

---

#### 2. Пошаговое решение

##### Шаг 1: Преодоление автоматического декодирования Flask (Особенность фреймворка)
При передаче параметров через URL веб-фреймворк Flask (бэкенд приложения) автоматически производит **однократное URL-декодирование** параметров из `request.args.get('file')` перед передачей их в код.

* При использовании двойного кодирования (например, `%252e%252e%252fflag%252etxt` для `../flag.txt`):
  1. Flask автоматически декодирует строку один раз $
ightarrow$ на вход функции `useless()` поступает `%2e%2e%2fflag%2etxt`.
  2. `file_param1 = ignore_it("%2e%2e%2fflag%2etxt")` успешно проходит (точек/слэшей в открытом виде нет).
  3. `file_param2 = unquote("%2e%2e%2fflag%2etxt")` декодирует её во временную строку `../flag.txt`.
  4. `file_param3 = ignore_it("../flag.txt")` обнаруживает явные символы `.` и `/`, блокирует запрос и возвращает ошибку.

##### Шаг 2: Проектирование вектора обхода через Тройное кодирование (Triple URL Encoding)
Чтобы обойти три этапа декодирования (одно во Flask + два внутри `useless()`) и избежать блокировки на обеих проверках `ignore_it`, необходимо применить **тройное URL-кодирование** спецсимволов:

1. Символы пути:
   * Точка `.` $
ightarrow$ `%2e` $
ightarrow$ `%252e` $
ightarrow$ **`%25252e`**
   * Слэш `/` $
ightarrow$ `%2f` $
ightarrow$ `%252f` $
ightarrow$ **`%25252f`**
2. Итоговая строка пути `../flag.txt` (файл флага в родительском каталоге) в тройном URL-кодировании принимает вид:
   👉 **`%25252e%25252e%25252fflag%25252etxt`**

##### Шаг 3: Трассировка выполнения в системе
* **Запрос в браузере:** `?file=%25252e%25252e%25252fflag%25252etxt`
* **На входе во Flask:** Автоматически декодируется один раз. Передает в `useless()` строку:  
  `%252e%252e%252fflag%252etxt`
* **`file_param1` (после `ignore_it`):** Явных точек/слэшей нет. Успешно возвращает `%252e%252e%252fflag%252etxt`.
* **`file_param2` (после первого `unquote`):** Декодирует `%25` в `%`. Возвращает `%2e%2e%2fflag%2etxt`.
* **`file_param3` (после `ignore_it`):** Явных точек/слэшей нет (вместо них `%2e` и `%2f`). Успешно возвращает `%2e%2e%2fflag%2etxt`.
* **`file_param4` (после второго `unquote`):** Декодирует `%2e` в `.` и `%2f` в `/`. Возвращает `../flag.txt`.
* **`file_param5` (после третьего `unquote`):** Строка `../flag.txt` возвращается без изменений.

##### Шаг 4: Получение флага
Отправляем GET-запрос с тройным URL-кодированием на эндпоинт чтения секретных сообщений:

```bash
curl "http://10.10.10.66/read_secret_message?file=%25252e%25252e%25252fflag%25252etxt"
```

Бэкенд успешно нормализует путь до `message/../flag.txt` (что эквивалентно чтению файла `flag.txt` в корневой директории приложения) и возвращает истинный флаг:

**`CTF{c0de_of_cod3_1n_4_s3cret}`**
